# DOX — MCP Directory

## Purpose

Model Context Protocol (MCP) server and tools layer that exposes all dspytools features for agent interoperability. Agents (OpenCode, Codex, Claude Desktop, web-based) connect via MCP to manage compiled programs, llama-cpp-server LoRA models, skills, GFL pipelines, evaluation, and DSPy inference.

## Ownership

Owns the MCP transport layer — both server (accepting inbound agent connections) and client (connecting to external MCP tool servers like git-mcp). Three source files:

| File | Role |
|------|------|
| `server.py` | Unified MCP server — exposes all dspytools features (built-in tools) over stdio or SSE transport. Uses `list_tools`, `call_tool`, `list_resources`, `read_resource` handlers. `create_mcp_server()` configures DSPy once at startup; `_dispatch()` owns the call-error classification. |
| `tools.py` | 65 MCP tool handlers with response caching (5s TTL), merged into BUILTIN_TOOLS from a base dict (7) + 3 sub-dicts: _EXTRA_TOOLS (31), _GRAPH_TOOLS (21), _FINAL_TOOLS (6). Covers: programs, signatures, modules, compiled runs, optimizers, skills, self-status, inspect history, evaluate, GFL synthesize, agent, mlflow_status, drift, sandbox, compile, archive search, validate_deploy, challenger_solver, meta_prompt_learn, opsd_purify, cache, LoRA, graph, memory. |
| `loader.py` | `MCPSessionPool` singleton — manages MCP client sessions to external servers (e.g. git-mcp), config-driven from `.mcp.json`. Converts external MCP tools to `dspy.Tool` via the event-loop-thread-aware `_make_sync_tool()` helper, which uses DSPy's `convert_input_schema_to_tool_args` and sanitizes MCP tool names to valid Python identifiers. |

## Local Contracts

- **Unified exposure**: `server.py` exposes `BUILTIN_TOOLS` from `tools.py` as the single entry point for agent interoperability.
- **Transport duality**: stdio transport for local agents (Claude Desktop, OpenCode); SSE transport for web-based agents. Both activated via `dspytools mcp serve --transport`. Both call `create_mcp_server()`, so both start with a configured DSPy.
- **Schema surface**: tools declare `description`, `inputSchema` and `annotations` only. `outputSchema` is deliberately **not** declared and **not** forwarded by `handle_list_tools` — results are free-form text, and declaring (but never sending) output schemas only created dead weight. Do not reintroduce the field without emitting it from `handle_list_tools`.
- **Lazy startup imports**: `import dspytools.mcp.server` must not pull MLflow. `commands.compile` (via `core.mlflow_tracker`), `dspytools.gfl` and `dspytools.evolve` all import the MLflow SDK at module scope, so `tools.py`/`server.py` import `_OPTIMIZER_SPECS` (`_optimizer_specs()`), GFL classes and optimizer/runtime classes *inside* the handlers that use them. Enforced by `tests/test_mcp_integrity.py::test_importing_the_server_does_not_import_mlflow`. Redis/FalkorDB clients are still imported at module scope (they connect lazily); changing that is a separate pass.
- **Response caching**: `tools.py` caches tool responses in-memory with 5-second TTL (`_CACHE_TTL`). Mutating tools invalidate relevant keys, and every memory mutation invalidates the `memory_*` glob (a bare `"memory_"` prefix matched nothing).
- **Optimizer names are single-sourced**: `optimizer_catalog()` (from `_OPTIMIZER_SPECS`) drives `list_optimizers`, the `dspytools://optimizers` resource and `compile_optimizer`. `cli_only` lists optimizer families that exist only as `dspytools compile <command>` commands (`better-together`, `ensemble`, `finetune`, `grpo`, `avatar`, `distill`, `flex`, `bootstrap-finetune`) and are explicitly **not** callable through the MCP tool. Underscore spellings (`bootstrap_few_shot`, …) are accepted as aliases only and are never advertised. A listed name must always resolve — list-then-compile used to fail on every entry.
- **Optimizer specs are process-wide state**: `_OPTIMIZER_SPECS[...]["params"]` is the CLI's own dict. `compile_optimizer` and `_make_optimizer_instance` copy it before attaching the teacher LM; writing `reflection_lm` (and its `api_key`) into the shared dict poisoned every later compile in the process.
- **Holdout before compile (Golden Rule 3)**: `compile_optimizer` and `lse_explore` call `get_holdout_gate().split(trainset, compile_id=...)` *before* constructing the optimizer and compile only on the train split; `lse_explore` scores each tree node on that holdout split.
- **Tool conversion**: External MCP tools are converted to `dspy.Tool` via the event-loop-thread-aware `_make_sync_tool()` helper in `loader.py` — it hand-builds `dspy.Tool(_call, name, desc, args, arg_types, arg_desc)` whose `__call__` dispatches `session.call_tool()` on the pool's dedicated MCP event-loop thread. The real blocker for `dspy.Tool.from_mcp_tool()` is **not** that it owns an event loop: `dspy.utils.mcp.convert_mcp_tool` builds a plain `async def` that awaits `session.call_tool` with no loop of its own. It is that `Tool.__call__` only handles a coroutine when `allow_tool_async_sync_conversion=True`, and then routes it through `_run_async_in_sync` → `asyncio.run()`, which creates a *new* loop while the MCP pipes answer on the pool's loop (`ClosedResourceError`). The async escape hatch is `tool.acall(...)` awaited on the pool's loop; the sync surface DSPy's `ReAct` needs goes through `_make_sync_tool`. The `tools.py` built-in handlers are plain synchronous functions wrapped in the `BUILTIN_TOOLS` dict with descriptions and input schemas.
- **Tool results are text-only; failures raise**: `_make_sync_tool._call` joins `result.content` text parts and returns a string, dropping image/file parts — a deliberate choice. A result with `is_error` raises `MCPToolError` (naming the tool and its text) instead of returning plausible-looking text, mirroring DSPy's own converter; the agent can no longer proceed as if a failed external call succeeded. Do not upgrade the text-only path to `dspy.Image`/`dspy.File` content parts without also moving off the `chat` API family — lm15's chat-completions presets declare `tool_result_media="reject"`, which aborts an agent mid-turn (see root AGENTS.md "Not adopted").
- **Tool schema fidelity**: `_schema_to_tool_args()` delegates to DSPy's `convert_input_schema_to_tool_args` (it returns `(args, arg_types, arg_desc)`) so property descriptions, types, and nested schema fragments survive. Hand-rolled `{name: {type: str}}` mappings are forbidden — they drop descriptions and mark every argument required. `dspy.Tool.as_function_tool()` derives JSON-schema `required` from the *absence* of a `"default"` key on an arg, so `_schema_to_tool_args` adds `default` (the schema's own default, else `None`) to every property the server did not list in `required`. Contract: optional MCP arguments must never be advertised as required. `tool_agent_run` reuses this helper so its tools keep their MCP `inputSchema` instead of being re-derived from the Python signature.
- **Tool name sanitization**: `_sanitize_tool_name(raw, taken)` maps MCP names to valid, unique Python identifiers — non-alphanumerics → `_`, leading digit → `_` prefix, keyword → `_` suffix, collisions → `_2`/`_3`. `dspy.ReAct` tolerates names like `git-mcp_list_files`; `dspy.RLM`/`dspy.Flex` raise `ValueError: Invalid tool name ...` unless the name is a valid identifier. Sanitize in the loader, never at the `commands/run.py` call site. The original MCP name stays in the tool description (`\n\nMCP tool name: <raw>`) and is what `_call` sends to the server.
- **Session lifetime**: `MCPSessionPool` connects once and keeps sessions for the life of the process. There is **no** keepalive sweep: `get_tools()` reconnects only when it has no cached tools or `force_reconnect=True`, so a working pool is never torn down and rebuilt mid-agent-turn (the old 300 s timer did exactly that). `refresh()` drops the cached tool list so the next `get_tools()` reconnects — that is all it does. Every cross-thread MCP operation is bounded by `MCP_CALL_TIMEOUT` (120 s) and raises `TimeoutError` instead of blocking the caller forever.
- **Connection failures are surfaced**: a per-server failure is recorded in `MCPSessionPool.failed_servers()` (`{"server", "error"}`), summarised by `describe_failures()`, logged at ERROR, and printed by `dspytools mcp tools` (both for an empty and for a partial tool list). An empty pool must never read as "that tool does not exist".
- **LM configuration**: `create_mcp_server()` calls `_ensure_lm_configured()` before the transport starts, so a fresh stdio/SSE server has an LM and `infer` does not fail with `ValueError: No LM is loaded`. Handlers keep their own guard: every LM-touching handler is wrapped in `_lm_tool`, which calls `_ensure_lm_configured()` (configure once under a lock, no-op when `dspy.settings.lm` is set) and converts a configuration failure into `_error()`'s in-band shape with a `dspytools configure lm set student …` hint. `dspy.configure` (via `setup_dspy`) raises `RuntimeError` off the configuring thread and `core/setup.py`'s documented fallback then writes `dspy.dsp.utils.settings.main_thread_config`, which is why the handler-side call stays guarded rather than calling `setup_dspy()` directly. Per-call isolation belongs to `dspy.context(...)` (e.g. `tool_agent_run` scopes the configured adapter that way).
- **GEPA needs a teacher**: `_make_optimizer_instance("gepa")` uses a five-argument metric (`_gepa_feedback_metric(gold, pred, trace, pred_name, pred_trace)`) and `reflection_lm=LMRegistry.get_teacher()`. GEPA rejects three-argument metrics (`TypeError`) and hard-asserts that a reflection LM exists (`AssertionError`). When no teacher is configured the helper raises an actionable `ValueError` — `tool_lse_explore` records the failed node, `tool_opsd_purify` surfaces the message, `tool_compile_optimizer` returns `_error()`. Never degrade silently to the student LM.
- **Agent adapter and failure payload**: `tool_agent_run` scopes the adapter `setup_dspy()` configured (`dspy.settings.adapter`, i.e. config `dspy.adapter`) with `dspy.context(adapter=...)` — it never hardcodes `BAMLAdapter` (that ignored the user's choice) and never mutates global settings. `max_iters` is an argument (default 8), and `tools` is a JSON array of this server's tool names. A failed forced submit raises a **plain `ValueError`**: `dspy/predict/react.py` raises `ValueError` from both `_forced_submit` paths ("ReAct failed to produce final outputs after …"), so the handler's broad `except` returns `{"error": "<Type>: <msg>", "exception", "last_model_output", "detail"}` rather than propagating to the MCP transport. `last_model_output` reads DSPy's `outputs` history key (falling back to `response.text` for alternate shapes).
- **No fabricated results**: `doctor`'s `dspy` check reports whether an LM is actually configured; `lse_explore` refuses to run without a trainset and scores nodes with `_measure()` (a real `dspy.Evaluate` on the holdout split); `meta_prompt_learn` returns `final_score: null` + `status: "not_evaluated"` when nothing was measured; `lora_unload_adapter` reports `status: "unsupported"` because llama.cpp has no unload endpoint. Never invent a score, a healthy check or a state change.
- **Error handling layering**: `tools.py` defines `_error(exception, detail=None)` → JSON string `{"error": ..., "detail": ...}`. Every in-band tool error uses it — `get_program_metadata`, `lora_load_adapter`, `compile_optimizer`, the `_lm_tool` guard and the rest — so clients can parse one shape. `server.py` does NOT import `_error`; `_dispatch()` returns its own dispatch errors, and the tool is resolved *before* the handler runs so the two never blur: unknown name → `{"error": "tool_not_found", "message", "hint", "available_tools"}`; handler `ValueError` (bad arguments, missing LM, dspy validation) → `{"error": "invalid_request", "tool", "message", "hint"}`; handler `RuntimeError`/`OSError`/`TypeError` → `{"error": "execution_failed", …}`; anything else → `{"error": "internal_error", …}`.
- **Resource URIs**: The unified server registers `dspytools://` resource URIs for programs (+ per-program `programs/{rid}`), config, MLflow, skills, evolve, GFL status, sandbox, and optimizers — 8 static + per-program entries. `dspytools://optimizers` serves `optimizer_catalog()`, exactly what `list_optimizers` returns. (llama-cpp/LoRA state is exposed via tools, not resources.)
- **Resource handler return type**: `@server.read_resource()` handler must return `Iterable[ReadResourceContents]` (list of `ReadResourceContents(content=..., mime_type=...)` dataclass instances from `mcp.server.lowlevel.helper_types`). This is the low-level SDK's expected format — returning `ReadResourceResult` or plain dicts causes client-side `TypeError`.

## Work Guidance

- When adding a new CLI command group that should be agent-accessible, register a corresponding tool handler in `tools.py` and add it to `BUILTIN_TOOLS` or `_EXTRA_TOOLS` / `_FINAL_TOOLS`. If the handler touches an LM, decorate it with `@_lm_tool`.
- A new optimizer belongs in `commands/compile.py`'s `_OPTIMIZER_SPECS` (one source for CLI + MCP) or in `_CLI_ONLY_OPTIMIZERS` when it is command-only. Never add a name to a second, hand-maintained list.
- When adding a new transport or modifying the MCP server initialization in `server.py`, keep `run_stdio()` and `run_sse()` signatures compatible with the CLI entry point in `commands/mcp.py`.
- Response caching TTL in `tools.py` is a simple time-based dict. For long-running servers, consider migrating to a proper cache with LRU eviction. Cache keys must be invalidated on any mutating tool call — use a glob when the key carries a suffix (`memory_*:{user_id}` shapes).
- `MCPSessionPool.get_tools()` is synchronous but internally runs an async event loop. Avoid calling from within an already-running async context without careful handling.

## Verification

- Functional smoke test: `dspytools mcp serve --transport stdio` then connect with an MCP client (Claude Desktop, MCP inspector, or an in-process `mcp.ClientSession` via `stdio_client`).
- Key assertions to re-verify after edits:
  - `list_tools` returns exactly 65 tools with correct names and descriptions, and no `outputSchema`
  - `list_resources` returns all 8 static resource patterns + per-program entries
  - `read_resource` for any URI returns `ReadResourceContents` (not `ReadResourceResult` or dict) — verified by client-side deserialization
  - `get_prompt` returns `content` as `{"type": "text", "text": "..."}` dict, not a raw string
  - All 3 prompts return valid `PromptMessage` objects with `TextContent` content
  - `call_tool` with an unknown tool returns `tool_not_found`; a handler `ValueError` returns `invalid_request` (never `tool_not_found`)
- Functional check (verified against a live stdio server): 65 tools, 8 static + N per-program resources, 3 prompts, resource reads and unknown-tool handling all work over `mcp.ClientSession`.
- Regression tests: `uv run --no-sync pytest tests/test_mcp_integrity.py -q` — optimizer-name agreement, startup LM configuration, dispatch classification, spec-params copy + holdout split, `_last_lm_output`, `inspect_history` sink, LoRA unload honesty, memory cache globs, `is_error` raising, pool timeout/session lifetime, failed-server surfacing, HotSwap singleton reuse, `agent_run` adapter/limits/schemas, no fabricated scores, uniform error shape, and the MLflow-free import.
- Legacy regression tests: `uv run --no-sync pytest tests/test_mcp_tools.py -q` — schema fidelity (descriptions/types/`required`/defaults), identifier sanitization + collision handling, `dspy.RLM` accepting a sanitized tool, `tool_agent_run` structured error on `AdapterParseError`, GEPA teacher requirement, and the `tool python-interpreter` sandbox shutdown.
